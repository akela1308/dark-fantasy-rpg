## Как давать задачи
Можно написать руководителю: «Доведи ходьбу Хольта и Рессы до готовности, распредели работу и проверь в игре». Он читает состояние специалистов, задаёт ограниченные поручения, ждёт результаты, проверяет и возвращает один отчёт.
Можно написать напрямую художнику: «Исправь одежду Рессы по эталону». Специалист выполняет только эту задачу в своей области. Если требуется работа другого профиля, формулирует передачу в своём итоге; руководитель увидит её при следующем обходе чатов.

Созданы отдельные равноправные чаты, а не постоянно работающие сотрудники. Каждый хранит собственный контекст. Общие договорённости и состояние записываются в файлы. Руководитель пользуется доступными инструментами чатов; если они недоступны в конкретном запуске, сообщает об ограничении, а не выдумывает отправку задачи. Автоматизации по расписанию не создавались. Модели не переопределялись.

## Задачи и инструменты

Правило от 25.11.2026 действует для всех пяти агентов, работающих по поручениям из чата «00 · Руководитель „Мортиса“».

- Формулируй поручение через конкретное действие, исходные материалы, ожидаемый результат и способ проверки. Роль указывает, кому поручена работа. Формулы вроде «ты лучший эксперт» не нужны.
- Определи, каким методом специалист решил бы задачу и проверил результат. Примени подходящие доступные и разрешённые инструменты. Например, воспроизведи игровой сбой в Chrome, сравни арт с утверждённым эталоном или сверь новый диалог с игровыми данными и лором. Если нужный инструмент недоступен, используй подходящую альтернативу или укажи, какая проверка осталась невыполненной.
- Объясняй итог простыми словами. Скажи, что игрок теперь видит или может сделать, чем это проверено и какие проблемы остаются. Указывай технические детали там, где они помогают повторить проверку или принять решение.

Пример поручения. «Открой сохранение перед Лешим в Chrome, выбери мирный ответ и обнови страницу при открытой реплике. Проверь, что Леший не вернулся и опыт начислен один раз. Приложи запись проверки к проверенному коммиту».

## Маршрут задачи
1. Руководитель читает AGENTS.md, ПРОДОЛЖИТЬ_CODEX.md, git status/log и статусы команды. Перед передачей задачи сверяет, не поручил ли Максим специалисту отдельную работу.
2. Даёт карточку: ID задачи, проблема, ожидаемый результат, разрешённые файлы/действия, ограничения, критерии приёмки, зависимости, режим «только анализ» или «изменение».
3. Анализ разных специалистов допускается параллельно. Правки, генерация файлов, сборка и Git в общей папке выполняются последовательно с блокировкой. Не создавать новые рабочие деревья или чаты без отдельного запроса владельца.
4. Исполнитель отвечает в своём чате: что изменено, пути/коммит, что проверено, что осталось. Не завершает пустым «готов» вместо работы, когда дана реальная задача.
5. Руководитель получает результат через wait_threads/read_thread. При необходимости отправляет уточнение. Не просит специалистов отвечать друг другу инструментами сообщений и не гоняет бесконечные «подтверждения получения».
6. QA проверяет конкретный коммит и критерии. После исправлений повторяет затронутые проверки. Руководитель сам проверяет diff, решает зависимости и завершает общий отчёт. Перед push проверяет ветку, не публикует main без явного согласия.

## Общая папка: один пишущий агент
При получении задачи на запись агент проверяет git status и атомарно создаёт каталог `mkdir .team-write-lock` в корне репозитория. Только успешный mkdir даёт право записи. Затем записывает в `.team-write-lock/owner.json` свой threadId/роль, задачу, начальный HEAD и время. Создание каталога и этой записи разрешено как часть захвата блокировки.

Если каталог существует, читать owner.json, проверить статус владельца через инструменты чатов. Не редактировать проект, не запускать сборку/установку/коммит. Можно продолжать независимый анализ; руководитель ждёт освобождения. Отсутствие owner.json тоже означает занятую блокировку (возможен незавершённый захват). Не удалять её автоматически.

После своего законченного шага и проверок удалить только собственный owner.json и пустой каталог через rmdir. Если агент был прерван, руководитель может освободить блокировку только после проверки, что владелец не выполняет работу, и сохранения незавершённых изменений. Не применять TTL и не «красть» блокировку у активного чата. При неизвестном владельце сначала выяснить состояние.

Тестировщик тоже получает блокировку на сборку, запись отчётов и запуск сценариев, создающих файлы. Read-only анализ репозитория и консультации блокировки не требуют. Несколько серверов не запускать на одном порту; останавливать только собственные процессы.

Это организационная защита от коллизий, не механическое ограничение файловых инструментов. Для настоящей изоляции параллельных правок позже можно по просьбе Максима настроить отдельные worktree.
